# Сайт Y LaYncher

Сайт лежит в папке `site/` и полностью статический: HTML, CSS, JS и шрифты.
Сервера и базы данных нет, поэтому падать нечему. Релизы подтягиваются из
GitHub Releases.

## Что уже есть

- `site/` — сам сайт (главная, возможности, скачивание, установка, FAQ).
- `site/releases.json` — снимок релизов GitHub, который создаётся при деплое.
- `site/config.js` — владелец/название репозитория и адрес сайта.
- `scripts/build-site.mjs` — собирает `releases.json` и `config.js` через GitHub API.
- `.github/workflows/pages.yml` — публикует сайт на GitHub Pages.
- `.github/workflows/release.yml` — собирает установщик по тегу `v*` и создаёт GitHub Release.

## Локальный просмотр

```powershell
npm.cmd run site
```

Откройте <http://localhost:4173/>. Команда соберёт данные и запустит мини-сервер
без дополнительных зависимостей.

Если репозиторий ещё не указан, сайт покажет подсказку «Подключите репозиторий».
Это нормально для локального запуска: при публикации через GitHub Actions
`config.js` заполнится автоматически. На GitHub Pages сайт также умеет определять
репозиторий из адреса `owner.github.io/repo/`, даже если `config.js` остался
шаблонным.

## Публикация на GitHub Pages — бесплатно

GitHub Pages раздаёт статику через CDN GitHub. Это бесплатно для публичных
репозиториев, не требует карты и не «засыпает», в отличие от бесплатных
динамических хостингов. Для приватного репозитория GitHub может потребовать
платный план — тогда используйте Cloudflare Pages или Netlify.

### 1. Загрузите проект на GitHub

Если репозитория ещё нет:

```powershell
git init
git add .
git commit -m "Y LaYncher 1.0.0"
git branch -M main
git remote add origin https://github.com/ВАШ_ЛОГИН/YLaYncher.git
git push -u origin main
```

> `node_modules/` и `dist/` уже исключены через `.gitignore` — загружать их не нужно.

### 2. Включите GitHub Pages

1. Откройте репозиторий на GitHub.
2. **Settings → Pages**.
3. В блоке **Build and deployment → Source** выберите **GitHub Actions**.
4. Ничего больше выбирать не нужно — workflow уже лежит в репозитории.

### 3. Запустите деплой

Сделайте любой коммит в `site/` или откройте **Actions → Deploy website →
Run workflow**. Через 1–2 минуты сайт будет доступен по адресу:

```text
https://ВАШ_ЛОГИН.github.io/НАЗВАНИЕ_РЕПОЗИТОРИЯ/
```

Точный адрес показывается в логе шага **Deploy to GitHub Pages**.

`config.js` и `releases.json` при деплое перезаписываются автоматически:
workflow подставляет текущий репозиторий и загружает релизы. Вручную править
их при использовании GitHub Actions не нужно.

## Как сайт получает релизы

При каждом деплое `scripts/build-site.mjs`:

1. запрашивает `https://api.github.com/repos/OWNER/REPO/releases`;
2. оставляет установщики (`.exe`, `.msi`, `.dmg`, `.AppImage`, `.deb`, `.zip` и т. п.);
3. записывает компактный `site/releases.json`;
4. сайт читает этот файл и рисует кнопки скачивания.

Дополнительно сайт умеет ходить в GitHub API напрямую, если `releases.json`
пустой или недоступен. Кнопка **«Обновить»** в блоке релизов тоже запрашивает API.

Почему это надёжно:

- основной источник — статический JSON, он лежит рядом с сайтом;
- GitHub API используется только как запасной вариант;
- даже при лимите API (60 запросов в час без токена) страница продолжает
  работать на сохранённом `releases.json`;
- сайт — это CDN-статика, у него нет процесса, который может упасть.

Workflow `pages.yml` пересобирает сайт не только при коммите, но и при событиях
`release: published/edited/deleted`. Поэтому новый релиз появляется на сайте
автоматически.

## Как выпустить новую версию

### Вариант А: автоматически, по тегу

1. Поднимите версию в `package.json`, например `1.0.1`.
2. Закоммитьте изменение.
3. Поставьте тег и отправьте его:

```powershell
git tag v1.0.1
git push origin v1.0.1
```

Workflow **Build release** на `windows-latest`:

- выполнит `npm ci`;
- соберёт NSIS-установщик (`npm run dist`);
- создаст GitHub Release и прикрепит `dist/*.exe`;
- после публикации релиза workflow Pages обновит сайт.

### Вариант Б: вручную

1. Соберите установщик локально:

```powershell
npm.cmd run dist
```

2. Откройте **Releases → Draft a new release**.
3. Укажите тег, например `v1.0.1`, и прикрепите файл
   `dist/Y LaYncher Setup 1.0.1.exe`.
4. Нажмите **Publish release** — сайт обновится сам.

> Не прикрепляйте к релизу `*.blockmap`, `latest.yml` и архивы с исходниками —
> сайт специально их игнорирует и показывает только установщики.

## Альтернативные бесплатные хостинги

Сайт можно положить куда угодно, где есть статика. GitHub Pages — самый простой
вариант, потому что релизы уже на GitHub.

### Cloudflare Pages

- **Build command:** `node scripts/build-site.mjs --repo=ВАШ_ЛОГИН/YLaYncher`
- **Build output directory:** `site`
- **Framework preset:** None
- Переменная окружения `YL_SITE_URL` — ваш адрес на `*.pages.dev` (необязательно).

Cloudflare Pages тоже бесплатен, работает на CDN и не «засыпает». Если не
хотите запускать сборку, просто загрузите папку `site` как есть — сайт возьмёт
релизы из GitHub API, но без токена действует лимит 60 запросов в час на IP.

### Netlify

Аналогично: publish directory `site`, build command можно оставить пустым или
указать `node scripts/build-site.mjs --repo=ВАШ_ЛОГИН/YLaYncher`.

### Свой домен

1. Купите домен (это единственная возможная плата).
2. В GitHub: **Settings → Pages → Custom domain**.
3. Пропишите CNAME у регистратора на `ВАШ_ЛОГИН.github.io`.
4. Включите **Enforce HTTPS**.

## Если что-то не работает

| Проблема | Что проверить |
| --- | --- |
| Сайт открывается, но пишет «Подключите репозиторий» | В `site/config.js` остался `YOUR_GITHUB_LOGIN`. При GitHub Actions проверьте, что workflow отработал без ошибок. |
| Нет релизов | В репозитории нет опубликованных Releases или к ним не прикреплён `.exe`. Черновики сайт не показывает. |
| Кнопка «Скачать» ведёт на GitHub | У релиза нет подходящего файла установщика. Прикрепите `.exe` к релизу. |
| Pages не деплоится | **Settings → Pages → Source** должен быть **GitHub Actions**. Проверьте лог workflow. |
| GitHub API отвечает 403 | Сработал лимит запросов. Сайт продолжит работать на `releases.json`; подождите час или запустите деплой заново. |
| Windows SmartScreen | Установщик не подписан платным сертификатом. Это ожидаемо: «Подробнее» → «Выполнить в любом случае». |

## Проверка перед публикацией

```powershell
node --check site/app.js
node --check scripts/build-site.mjs
node --check scripts/preview-site.mjs
npm.cmd run site
```

Откройте страницу, проверьте мобильную ширину, кнопки скачивания и блок релизов.
